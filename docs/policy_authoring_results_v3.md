# 정책 작성 실험 결과 — 172콜, 4모델

설계: [`docs/policy_authoring_v3.md`](policy_authoring_v3.md) (결과 보기 전 고정)
산출물: `experiments/policy-authoring/policies.jsonl` · `manifest.json`
**파싱 실패 0 / 기술 실패 0.**

## 0. 한 문장

로컬 모델 4종 중 어느 것도 인간 검토자의 최소권한 정책을 재현하지 못했고
(**정확 일치 0/172**), 실패의 형태가 "너무 관대함"이 아니라 **"다른 집합을 고름"** 이었다.

## 1. 두 오류가 동시에 크다

![오류 방향](figures/fig_policy_error_directions.png)

| 모델 | 허용 필드 | 과잉 허용 | └ 민감 | 과잉 차단 | 재현율 |
|---|---|---|---|---|---|
| `llama3.1:8b` | 6.8 | 4.51 | 0.02 | 6.28 | 0.30 |
| `qwen2.5:3b` | 4.7 | 3.05 | 0.14 | 6.95 | 0.20 |
| `qwen2.5:7b` | 4.0 | 2.42 | 0.14 | 7.05 | 0.21 |
| `qwen3:8b` | 7.5 | 4.40 | **0.81** | 5.47 | 0.39 |
| **전체** | 5.7 | 3.59 | 0.28 | 6.44 | 0.27 |

*(인간 검토자 기준 8.6 필드. 시나리오당 평균)*

여기서 중요한 것은 두 열이 **동시에** 크다는 점이다. 모델이 사람보다 관대하기만 했다면
과잉 허용만 컸을 것이고, 소심하기만 했다면 과잉 차단만 컸을 것이다. 실제로는 시나리오당
평균 3.6개를 더 주면서 6.4개를 빼먹는다 — **더 넓거나 좁은 정책이 아니라 다른 정책**이다.

Jaccard 0.18(도메인 단위 0.33)이 이를 요약한다.

### 1.1 절반은 도구 혼동이다

빗금이 도메인 단위 재채점이다. 과잉 허용 3.59 → **1.53**, 과잉 차단 6.44 → **4.81**.

검토자들은 `search_contacts`(발견: `id`·`name`)와 `get_contact`(상세)을 나눠 라벨링했고
(두 도구가 모두 라벨된 17개 시나리오 **전부**), 모델은 이 구분을 따르지 않는다. 과잉 허용의
**57%가 필드 오판이 아니라 도구 선택** 문제다.

이건 처방이 다르다. 정책 문법을 스키마로 검증하면 잡히는 종류이지, 민감도 판단을 못 하는
문제가 아니다.

## 2. 모델은 과제를 읽고는 있다

신호탐지로 확인했다. "검토자가 필요하다고 한 필드를 모델이 포함한 비율"(hit)과
"불필요하다고 한 필드를 포함한 비율"(false alarm)의 차이:

| 모델 | hit | false alarm | 차이 |
|---|---|---|---|
| `llama3.1:8b` | 0.381 | 0.120 | 0.261 |
| `qwen2.5:3b` | 0.375 | 0.060 | 0.315 |
| `qwen2.5:7b` | 0.357 | 0.054 | 0.303 |
| `qwen3:8b` | 0.448 | 0.124 | 0.325 |

네 모델 모두 차이가 뚜렷하다. **무작위나 고정 습관이 아니라 과제에 반응한다.**
다만 hit 자체가 0.36~0.45로 낮다 — 방향은 맞는데 **감도가 낮다.**

## 3. 빠뜨리는 것 — 식별자가 검색 연결을 끊는다

![누락 필드](figures/fig_policy_omitted_fields.png)

누락은 특정 필드에 몰린 게 아니라 **전반적으로 높다**(상위 필드 75~97%).
그중 식별자가 중요한 이유는 더 많이 빠져서가 아니라(`contact.role` 97%가 더 높다)
**빠졌을 때의 결과가 종류부터 다르기** 때문이다.

| 필드 | 누락 비율 |
|---|---|
| `email.id` | 99/104 (95%) |
| `calendar.id` | 55/60 (92%) |
| `contact.id` | 132/156 (85%) |

`id`가 없으면 검색 결과를 상세 조회로 이어갈 수 없다. 표시 필드 하나를 잃는 것이 아니라
**검색 연결 자체가 끊긴다.**

### 3.1 본 실험과 같은 맹점

이 결과는 본 실험(2×2, 688 runs)의 미해결 관찰과 정확히 맞물린다.

| | 본 실험 (행동) | 정책 실험 (작성) |
|---|---|---|
| 관찰 | 평균 도구 호출 **1.45회**, 62%가 단 1회 | 식별자 **85~95% 누락** |
| | 발견→상세 체인 완주 **8.6%** (59/688) | |

**행동할 때 검색을 연결하지 못하고, 정책을 쓸 때 연결에 필요한 필드를 빼먹는다.**
두 실험은 서로 독립적으로 실행됐는데 같은 결함을 가리킨다 — 모델은 업무의 *정보 내용*은
읽지만 그 정보에 도달하는 *검색 절차*를 계획하지 않는다.

어느 한 실험만으로는 나오지 않는 결론이다. 본 실험만 보면 "성공률이 낮다"에서 끝나고,
정책 실험만 보면 "재현율이 낮다"에서 끝난다.

## 4. 민감 필드 — 위험은 집중돼 있다

![민감 필드](figures/fig_policy_sensitive_grants.png)

전체 콜의 **18.0%** 가 검토자가 금지한 민감 필드를 최소 하나 허용했다. 그런데 이 위험은
고르게 퍼져 있지 않다.

**모델별로 집중** — `qwen3:8b` 0.81 vs 나머지 0.02~0.14. 한 모델이 나머지 셋을 합친 것의
2.7배다.

**필드별로 집중**

| 금지 민감 필드 | 허용률 |
|---|---|
| `email.body` | 35/144 (**24.3%**) |
| `calendar.events[].participants` | 2/8 (25.0%, 표본 8) |
| `contact.phone` | 7/136 (5.1%) |
| `contact.notes` | 4/148 (2.7%) |

**`email.body` 가 위험 지점이다.** 연락처의 `phone`·`notes`는 모델도 대체로 뺀다 —
"개인정보"로 인식하기 쉬운 형태이기 때문으로 보인다. 반면 메일 본문은 업무 문서로 보이고,
실제로 그 안에 민감 정보가 들어 있다는 판단은 내용을 봐야 가능하다.

## 5. 어휘 밖 경로는 환각이 아니라 문법 오류

어휘에 없는 경로를 쓴 콜은 2.9%뿐이고, 그중 **7/8(88%)이 실재 필드의 표기 오류**였다.

- `search_calendar.events[].participants[]` — 대괄호 중복
- `search_calendar.time` / `.title` / `.participants` — `events[].` 접두 누락
- `get_contacts.name` — 도구명 오타(복수형)

실재하지 않는 필드는 `search_calendar.slots[].start_time` 1건뿐이다.

모델은 **무엇을 원하는지 알고 표기를 틀린 것**이다. 정책을 적용하기 전 스키마로 검증하면
잡히는 종류이지, 상상한 데이터 위에서 추론하는 것이 아니다.

## 6. 라벨 난이도 신호 (정직하게 보고할 것)

**43개 시나리오 중 36개에서 4모델 전원이 과잉 허용**했고, 4모델 전원이 정확히 일치한
시나리오는 **0개**다.

전원 일치 불일치를 전부 모델 오류로 읽는 것은 무리다. 우리 라벨이 모델들보다 일관되게
엄격하다는 뜻일 수도 있다. 다만 라벨은 2인 독립 검토와 14행 조정 기록을 거쳤고, 이 실험을
위해 수정하지 않았다. **판단을 유보하고 수치를 그대로 보고한다.**

## 7. 이 결과가 말하는 것 — 그리고 말하지 않는 것

### 말할 수 있는 것

정책 작성을 모델에 그대로 맡기면 **양방향으로 실패**한다. 업무는 깨지고(재현율 0.27),
민감 필드는 18%의 확률로 새어 나간다. 따라서 최소권한 정책의 작성 단계는 아직 사람의
자리다.

다만 **어디에 사람이 필요한지가 좁혀진다.**

| 실패 | 어떤 개입이 필요한가 |
|---|---|
| 도구 혼동 (오류의 57%) | **기계**가 잡는다 — 적용 전 스키마 검증 |
| 경로 표기 오류 (2.9% 중 88%) | **기계**가 잡는다 — 같은 검증기 |
| 식별자 누락 | **기계**가 잡는다 — 검색 연결 가능성 정적 확인 |
| `email.body` 허용 (24.3%) | **사람**이 봐야 한다 — 내용을 봐야 판단 가능 |
| 나머지 필드 판단 | 사람 검토, 단 우선순위는 낮음 |

즉 **"AI 초안 → 스키마 검증기 → 사람은 자유서술 필드만 승인"** 이라는 분업이 이 데이터에서
직접 도출된다. 사람이 43개 시나리오 × 8.6필드를 전부 보는 대신, 본문·메모 같은 자유서술
필드에 집중하면 된다.

### 말할 수 없는 것

- **일반화.** 소형 로컬 모델 4종, 합성 단일 도메인, 한국어, 단발 호출이다.
  상용 대형 모델이나 예시를 준 프롬프트에서는 달라질 수 있다.
- **"AI가 정책을 못 쓴다"** 는 결론. 측정한 것은 *우리 라벨과의 일치*이지 정책의 절대적
  타당성이 아니다. 6절의 유보가 여기에 걸린다.
- **효용 비용.** 모델 정책을 실제로 적용했을 때 업무가 얼마나 깨지는지는 측정하지 않았다.
  본 실험의 `task_success`가 5% 바닥이라 그 위에서는 차이가 드러나지 않는다.

## 8. 재현

```bash
python run_policy_authoring_v3.py --experiment-dir experiments/policy-authoring \
    --model qwen2.5:3b --model qwen2.5:7b --model llama3.1:8b --model qwen3:8b
python analysis_policy_authoring_v3.py --experiment-dir experiments/policy-authoring
python figures_policy_authoring_v3.py --experiment-dir experiments/policy-authoring
```

`temperature=0.0` / `seed=0` / `num_predict=1000`. manifest가 시나리오 CSV 해시·프롬프트
해시·어휘·실행 파라미터를 동결한다.
