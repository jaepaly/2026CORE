## [좌측 1/3] 문제 · 설계

### 왜 이 문제인가

AI 에이전트에 메일·주소록·캘린더 도구를 연결하면, **업무에 필요 없는 개인정보까지 모델
컨텍스트로 들어간다.** 현장의 표준 대응은 시스템 프롬프트에 "최소한만 읽어라"라고 쓰는 것이다.

**이 대응이 실제로 듣는가? 듣지 않는다면 대안은 무엇이고, 그 대안은 누가 만드나?**

### 왜 사내 업무 데이터인가 ★ (좌측 최상단)

개인정보 통제는 보통 **데이터 유형**으로 한다(주민번호·전화번호 패턴 탐지). 사내 데이터에서는 어긋난다.

**① 위험이 자유서술 업무 필드에 쌓인다.**
연락처 `notes` 실제 내용: `"출산 휴가 중 복귀 예정"` · `"식사 알레르기: 견과류"`
→ **어떤 PII 패턴에도 안 걸린다.** 그런데 정형 PII보다 민감하다.

| | 자유서술 (`notes`·`body`) | 정형 (`phone`) |
|---|---:|---:|
| 금지 라벨 | **67%** | 33% |
| 실제 전달 | **63%** | 37% |

**② 민감도가 업무에 따라 뒤집힌다.**
`email.body` 허용 5 / 금지 36 · `events[].participants` **허용 6 / 금지 2**
→ 전역 규칙으로 표현 불가

> **사내 도메인은 유형 기반 탐지가 아니라 업무 단위 필드 수준 권한 정책을 요구한다.**
> 최소권한 원칙(Saltzer & Schroeder 1975)을 데이터 필드 단위로 내린 형태.

### 미리 밝히는 것 — 무엇이 자명한가

> **필드 projection이 전달을 막는 것 자체는 발견이 아니다.**
> 허용 필드를 정하고 나머지를 지우면 전달되지 않는 것은 정의상 참이며,
> C·D = 0.00 은 **구현이 설계대로 작동했다는 검증**이다.
>
> 자명하지 않은 것은 ① 프롬프트 방어의 실제 효과 ② **정책을 누가 쓰는가**
> ③ 두 층위의 실패가 같은 원인인가 — 이 셋이다.

*(두 박스를 왼쪽 상단에 이 순서로 배치. 먼저 "왜 회사 데이터냐"에 답하고, 이어 심사위원의 첫 질문을 우리가 먼저 던진다.)*

### 연구 1 — 집행 (사전 등록 2×2)

| | projection 없음 | task-aware projection |
|---|---|---|
| **중립 프롬프트** | **A** | **C** |
| **최소화 지시** | **B** | **D** |

primary 비교 **A vs C만**, primary endpoint **`safe_completion`**(업무 성공 ∧ 업무외 민감 전달 0)

### 연구 2 — 작성

같은 시나리오·데이터·라벨을 **읽기만** 한다. 업무 요청문 + 도구별 반환 가능 필드 40개를 주고
모델이 직접 최소권한 정책을 쓰게 한 뒤 인간 라벨과 비교.

### 품질 게이트 (방법론 기여)

1. **시나리오 라벨** — 2인 독립 검토 + 자동 게이트. "도구 0회 호출 에이전트" 통과율 **0%** 강제 (승인 43 / 폐기 5)
2. **모델 파일럿** — tool-call 형식 준수 ≥80%만 채택(`mistral:7b` 0%, `qwen2.5:14b` 12% 제외). "전달 0"이 프라이버시가 아니라 **형식 미준수**인 오염 차단
3. **공정성 조건** — 검토자 라벨이 전부 모델에게 제시된 어휘 안에 있을 것, 프롬프트에 정답이 없을 것 (자동 테스트로 강제)
4. **값 없는 산출물** — 필드 경로·ID·해시·카운트만. 합성 데이터 문자열 174개 중 산출물 등장 **0건** 확인

## [우측 1/3] 공존의 형태 · 한계

### ⑤ 모델은 실패를 알리지 않는다 — 대신 지어내지도 않는다 ★

정책을 집행하면 모델은 **정보가 부족한 채로** 업무를 만난다. 그때 "못 하겠다"고 말하는가?

| 조건 | 한계 인정 | **무신호** | **값 누출** |
|---|---:|---:|---:|
| A 중립 | 43 | **119** | **0** |
| B 지시 | 54 | **108** | **0** |
| C projection | 44 | **121** | **0** |
| D 둘 다 | 47 | **118** | **0** |

**실패의 약 70%가 무신호** — 한계 인정은 27~33%뿐이고 조건과 무관하다.
projection이 정보를 줄여도 모델이 그 사실을 **알리게 되지는 않는다.**

**그런데 값 누출은 네 조건 모두 0** — 전달되지 않은 민감 값이 답변에 나타난 run 0건.
인터페이스에서 막은 것은 **답변 수준에서도 유지된다.**

> **"AI한테 맡겨도 되나?"의 답이 갈린다.**
> 유출 억제는 **맡길 수 있고**, 실패 감지는 **맡길 수 없다.**
> → 감지 책임은 모델의 자기보고가 아니라 **감사 로그**에 있다. 4축 중 감사 로그가 필요한 이유.

*(보조 분석 — 끝맺음 분류는 사전 등록 이후 추가된 계측이라 동일 설정 재실행 세트 688 runs 기준)*

### ⑥ 위험은 한 곳에 몰려 있다

전체 콜의 **18.0%** 가 금지된 민감 필드를 허용. 그런데 균등하지 않다.

| 금지 민감 필드 | 허용률 |
|---|---:|
| **`email.body`** | **35/144 (24.3%)** |
| `contact.phone` | 7/136 (5.1%) |
| `contact.notes` | 4/148 (2.7%) |

전화·메모는 모델도 "개인정보"로 알아본다. **메일 본문은 업무 문서로 보이고,
그 안에 민감 정보가 있는지는 내용을 봐야 안다.**

### ⑦ 그래서 사람은 어디에 필요한가 ★ 결론

실패를 원인별로 분해하면 **사람이 볼 지점이 좁혀진다.**

| 실패 | 규모 | 누가 잡나 |
|---|---|---|
| 도구 혼동 | 과잉 허용의 **57%** | ⚙️ **기계** — 스키마 검증 |
| 경로 표기 오류 | 어휘 밖의 **88%** | ⚙️ **기계** — 같은 검증기 |
| 식별자 누락 | 85~95% | ⚙️ **기계** — 연결 가능성 정적 확인 |
| **`email.body` 허용** | 24.3% | 👤 **사람** — 내용 판단 필요 |

**그 검증기를 실제로 만들었다** (`policy_lint_v3.py`) — 라벨·모델·run 을 보지 않는 정적 검사

| | 통과 (54) | 거부 (118) |
|---|---:|---:|
| 평균 재현율 | **0.388** | 0.221 |
| **민감 필드 허용률** | **7.4%** | **22.9%** |

- 인간 라벨 **43개 중 0개** 지적 → 관행이 아니라 실행 가능성만 판정
- 모델 정책 **172 → 54개**로 축소 (69% 기계 거부)
- 민감도 라벨을 **안 보는데도** 민감 허용률 3배 감소

> ### 모델 초안 → 스키마 검증 → **사람은 자유서술 필드만 승인**
>
> 사람이 43×8.6 필드를 전수 검토하는 대신 **본문·메모에 집중**하면 된다.
> 여기에 값 없는 감사 로그(688 runs)를 결합하면 네 축의 역할이 수치로 규정된다 —
> **사람**(정의·승인) · **시스템**(집행) · **모델**(수행·초안) · **감사 로그**(검증).

*(규범적 제안이 아니라 관측된 실패 분포에서 도출했고, "기계" 항목은 구현·평가까지 마쳤다.)*

### ⑧ 그래서 무엇이 새로운가 ★ (심사위원 예상 질문 대응)

> **"이거 그냥 API 연결하면 누구나 할 수 있는 거 아닌가?"**

새 방어 기법을 제안하는 게 아니다(projection이 막는 건 정의상 참 — 좌측에서 먼저 인정).
새로운 것은 **사내 도메인을 특별하게 만드는 성질과 자동화가 멈추는 지점이 같은 곳으로 수렴**한다는 것.

```
① 자유서술 필드에 위험 집중(67%) + 과제 상대적 민감도  →  전역 규칙으로 표현 불가
② 그래서 과제 단위 정책 필요                          →  사람이 써야 함 = 병목
③ 모델에게 시켰더니                                   →  못 씀 (0/172)
④ 그런데 실패가 갈림                                  →  기계 몫(172→54) / 사람 몫
⑤ 사람 몫이 email.body 24.3%에 집중                   →  ①에서 지목한 바로 그 필드
```

> **사내 도메인을 특별하게 만드는 그 성질이, 곧 자동화가 멈추는 지점이다.**

이 연결은 **과제별 사람 라벨 + 필드 단위 전달 계측이 둘 다 있어야** 보인다.
출력에서 유출을 보는 기존 평가로는 ③~⑤가, 전역 PII 분류로는 ①이 관측되지 않는다.
→ **"기존 연구를 회사 도메인에 적용"이 아니라 "도메인 성질에서 출발해 자동화 경계를 데이터로 찾음".**

*(경계값 172→54, 24.3%는 우리 라벨·이 도메인의 값. 일반화를 주장하는 건 숫자가 아니라 **그 경계를 찾는 절차**.)*

### 한계 — 숨기지 않는다

- **primary 유의하지 않음(p=0.070).** 업무 성공률 3~6%가 직접 원인. validator를 느슨하게 하면 성공률은 오르지만 v2에서 측정 자체가 무너졌으므로 선택하지 않았다
- **비교 기준을 우리가 만들었다.** 43개 중 **36개에서 4모델 전원이 과잉 허용** — 우리 라벨이 일관되게 엄격할 가능성을 배제할 수 없다. 판단 유보하고 수치를 그대로 보고
- 소형 로컬 모델 4종 · 합성 단일 도메인 · 한국어 · 단발 호출
- 인젝션 차단은 설계 수준만, 행동 수준은 미검증
- **전달량 절대값은 실행 하드웨어에 의존한다.** 모델을 세 머신에 나눠 돌렸고, 단일 머신 재실행 시 A 0.50→0.44
  (거의 전부 qwen2.5:7b). 같은 머신 반복은 172/172 완전 동일 → 비결정성이 아니라 머신 차이.
  **순위·부호는 세 실행 모두 불변**(C·D 언제나 0.00, B가 A보다 낮아지지 않음). 절대값을 단일 환경 재현값으로 인용 금지

3. 상용·대형 모델 확장
