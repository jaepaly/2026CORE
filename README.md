# 업무를 돕는 AI는 어디까지 읽어야 하는가?

![AI 에이전트 개인정보 노출 연구](docs/figures/readme_hero.png)

도구 사용형 AI 에이전트가 이메일·주소록·캘린더에 접근해 업무를 수행할 때, **민감정보 노출을 막는 방법으로 "모델에게 적게 읽으라고 지시하는 것"과 "도구가 애초에 민감 필드를 반환하지 않게 설계하는 것" 중 무엇이 실제로 작동하는가**를 사전 등록 실험으로 측정한 학부 연구입니다.

> **결론 먼저 (v3 본 실험 · 4모델 688 runs · 기술 실패 0)**
> 1. **필드 projection은 실제 전달되는 민감 필드를 0으로 만든다** — A 0.50 → C 0.00, 차이 0.50 (95% CI 0.35~0.65), 4모델 전 계열 동일.
> 2. **프롬프트 최소화 지시는 전달을 줄이지 못했다** — 중립 A 0.50 vs 지시 B 0.52.
> 3. **단, 사전 등록한 primary(안전한 업무 완수)는 유의하지 않았다** — McNemar p = 0.070. 업무 성공 자체가 3~6%로 드물어 검정력이 부족했다. 확정적으로 말할 수 있는 것은 1·2번(전달 계층)이다.

## 1. 연구 질문

1. **프롬프트 최소화 지시**는 실제로 모델에게 전달되는 민감 필드를 줄이는가?
2. **task-aware 필드 projection**(도구가 업무에 필요한 필드만 반환)은 모델과 무관하게 민감 전달을 줄이는가?
3. 두 방어는 업무 완수, 그리고 **"민감 전달 없는 업무 완수"**(`safe_completion`)에 어떤 영향을 주는가?

핵심 구분은 **"모델의 순응에 기대는 방어"와 "인터페이스에서 집행하는 방어"** 를 같은 환경에서 분리 비교하는 것입니다.

## 2. 어떻게 여기까지 왔나 — v2 탐색에서 v3 사전 등록으로

처음 설계(v2, 768 runs)를 감사하다가 **세 가지 교란**을 발견해 실험 전체를 재설계했습니다. 이 이력 자체가 연구의 일부입니다.

| v2에서 발견한 교란 | v3에서의 교정 |
|---|---|
| **조건 A가 무방어가 아니었다** — [`llm_agent_v2.py:184`](llm_agent_v2.py#L184)의 기본 프롬프트가 *모든 조건*에 "최대한 적은 개인정보로", "불필요한 전체 열람은 피하세요"를 넣고 있었다 | 프롬프트 축을 분리해 **진짜 중립 조건 A**를 만들었다. "지시 유무" 대조가 v3에서 처음 성립 |
| **C/D가 필드 필터와 도구 차단을 함께 바꿨다** — 어느 기전의 효과인지 분리 불가 | v3는 **projection 축만** 조작한다. 네 조건 모두 `tool_denial: none` |
| **성공 판정이 과제 문구 복창만으로 통과** — 검색 능력을 측정하지 못함 | 데이터에서만 얻을 수 있는 값을 요구하도록 validator를 재작성하고, **자동 게이트**로 강제 |

그래서 v2 수치는 인과 근거로 인용하지 않습니다(부록 A에 보존). v3는 분석 전에 프로토콜·시나리오 해시를 manifest에 동결한 **사전 등록** 실험입니다.

## 3. 실험 설계 (v3)

![연구 설계](docs/figures/readme_method.png)

### 3.1 사전 등록 2×2

두 축을 **독립적으로** 조작합니다. 네 조건 모두 도구 차단(`tool_denial`)은 없습니다 — projection 효과만 분리하기 위해서입니다.

| | projection 없음 | task-aware projection |
|---|---|---|
| **중립 프롬프트** | **A** (위험 상한선) | **C** |
| **최소화 지시** | **B** | **D** |

- **primary 비교: A vs C만**, primary endpoint: **`safe_completion`**(업무 성공 ∧ 업무외 민감 필드 전달 0). 나머지는 secondary.
- projection은 시나리오별로 **사람이 승인한 `allowed_field_paths`만** 도구가 반환하게 합니다. 예) 회의 조율 과제에서 `get_contact`은 `id`·`name`·`email`·`department`만 반환하고 `phone`·`notes`·이메일 `body`는 제거.
- 프롬프트 해시를 조건별로 검증해 **A==C, A≠B**를 manifest에 고정했습니다.

### 3.2 데이터 환경

합성 워크스페이스 55항목 — 연락처 15 · 이메일 33 · 캘린더 7.
연락처 `notes`에 임신·병원 진료·알레르기 등 민감 PII, 이메일 5건(`e17`·`e29`·`e31`·`e32`·`e33`)의 `body`에 프롬프트 인젝션 페이로드.
도구 6종: `search_contacts`/`get_contact`/`search_emails`/`get_email`/`search_calendar`/`create_event`.

### 3.3 게이트 ① 시나리오 라벨 — 2인 독립 검토 + 자동 검증

48개 업무 시나리오마다 필요 레코드·허용 필드·성공 validator를 **두 사람이 독립 라벨링하고 교차 검토**했습니다. 그 위에 [`validate_review_v3.py`](validate_review_v3.py)가 기계적으로 차단합니다:

| 검사 | 막는 것 |
|---|---|
| B1 prompt-echo | 과제 문구 복창만으로 통과하는 validator |
| B2 unsatisfiable | 허용 필드로는 풀 수 없는 과제 |
| B4 forbidden 모순 | 허용한 필드를 금지해 정상 답변을 유출로 오판 |
| B5 민감 필수지정 | 업무와 무관한 개인정보를 "필수"로 지정 |
| B9 발견 경로 없음 | 상세조회만 허용해 C/D가 추측에 의존하게 되는 라벨 |

핵심 판정은 **"도구를 0회 호출한 에이전트의 통과율이 0%"** 입니다. 최초 제출은 이 값이 **83%**였고(즉 라벨이 검색 능력을 측정하지 못했고), 수정 후 **0%**가 되어 게이트를 통과했습니다.
→ **승인 43행 / 폐기 5행**(`s3`·`s13`·`s15`·`s17`·`s18` — 과제가 요구하는 레코드가 합성 데이터에 없음. 실행 전 결정이며 행은 `discarded`로 남겨 추적됩니다.)

### 3.4 게이트 ② 모델 파일럿 — "전달 0"이 프라이버시가 아닌 경우 배제

일부 모델은 도구를 호출하지 않고 자연어로 "검색하겠습니다"라고 **서술만** 합니다. 그러면 "민감 전달 0"이 프라이버시가 아니라 **형식 미준수**가 됩니다. 중립 조건에서 **valid tool-call ≥80%, 오류 ≤5%** 를 요구했습니다.

- 채택(4종): `qwen2.5:3b` · `qwen2.5:7b` · `qwen3:8b` · `llama3.1:8b` (3계열, 3b~8b)
- 제외: `mistral:7b`(0%) · `qwen2.5:14b`(12%) · `qwen3:14b`(think 미사용 시 0%)

### 3.5 실행 규모와 설정

**4모델 × 43시나리오 × 4조건 × 1 seed = 688 runs, 기술 실패 0.**
전 모델 동일 설정: `max_turns=4` / `temperature=0.0` / `num_predict=1000` / `seed=0` / `think=false`.
`runs.jsonl`에는 **원문 값이 없습니다** — 필드 경로·레코드 ID·해시·카운트만 저장하는 privacy-safe 로깅입니다.

### 3.6 3계층 분리 보고

결과를 하나로 합치지 않고 세 층으로 나눠 보고합니다.

- **전달(delivery)** — 도구 경계에서 모델에게 실제 반환된 업무외 민감 필드 수
- **행동(behavior)** — validator 기준 업무 성공률
- **엔드포인트** — `safe_completion`

## 4. 결과

![조건별 3계층](docs/figures/fig_v3_layers.png)

| 계층 | A (중립) | B (지시) | C (projection) | D (둘 다) |
|---|---:|---:|---:|---:|
| **전달** — run당 민감 필드 | 0.50 | 0.52 | **0.00** | **0.00** |
| **행동** — task 성공률 | 0.06 | 0.05 | 0.04 | 0.03 |
| **엔드포인트** — `safe_completion` | 0.01 | 0.00 | **0.04** | 0.03 |

### 4.1 확인된 것

**① 필드 projection은 민감 전달을 완전히 제거한다.**
A−C 차이 **0.50 (95% CI 0.35~0.65)** — CI가 0을 여유 있게 배제합니다. v3는 projection 축만 조작했으므로 이 효과는 projection에 귀속됩니다. 모델별로도 방향이 일치합니다:

| 모델 | A | B | C | D |
|---|---:|---:|---:|---:|
| qwen2.5:3b | 0.40 | 0.30 | 0.00 | 0.00 |
| qwen2.5:7b | 0.56 | 0.53 | 0.00 | 0.00 |
| qwen3:8b | 0.47 | 0.51 | 0.00 | 0.00 |
| llama3.1:8b | 0.58 | **0.72** | 0.00 | 0.00 |

**② 프롬프트 최소화 지시는 전달을 줄이지 못했다.** (secondary)
진짜 중립인 A(0.50)와 지시 조건 B(0.52)가 같은 수준입니다. `llama3.1:8b`에서는 지시 조건의 전달이 오히려 높았습니다(0.58 → 0.72). v2에서 불가능했던 "지시 유무" 대조가 성립했고, 답은 부정적입니다.

**③ A/B는 업무에 성공해도 안전하지 않다.**
성공한 run에도 민감 필드가 함께 전달돼 `safe_completion`이 A 0.01 / B 0.00에 그칩니다. C/D만 0.04 / 0.03을 기록했습니다.

### 4.2 primary는 유의하지 않았다 (정직 보고)

사전 등록한 **A vs C (`safe_completion`)** 는 McNemar **p = 0.070** (risk diff −0.035) — 방향은 C 우세지만 α=0.05를 넘지 못했습니다.

원인은 **기저 업무 성공률이 3~6%로 낮다**는 것입니다. 성공 자체가 드물면 "안전한 성공"의 조건 간 차이를 검출할 표본이 부족합니다. 따라서 *"projection이 안전한 완수를 늘린다"* 는 **이 표본에서 입증되지 않았다**고 쓰는 것이 맞습니다. 확정적으로 말할 수 있는 것은 전달 계층(4.1)입니다.

> validator를 느슨하게 하면 성공률은 오르지만, v2에서 확인했듯 측정 자체가 무의미해집니다(prompt-echo 83%). 검정력을 위해 측정 타당성을 포기하지 않았습니다.

### 4.3 설계 수준에서 추가로 성립하는 것 (모델 실행과 무관)

노출 **용량**(worst-case 상한)은 정책 정의에서 직접 계산됩니다([`interface_risk.py`](interface_risk.py)) — 필드 필터 없는 정책은 민감필드 용량 **151.5** / 악성 본문 전달 가능 **5건**, 필드 최소권한은 **10.5 / 0건**.

## 4.4 그럼 그 정책은 누가 쓰나 — 정책 작성 실험

앞의 결과에서 projection이 민감 전달을 0으로 만든 것 자체는 **발견이 아니라 구현 검증**이다.
허용 필드를 정하고 나머지를 지우면 전달되지 않는 것은 정의상 당연하다. 의미 있는 대조는
그 옆에 있다 — 현장의 기본 방어인 "AI에게 조심하라고 지시한다"가 무효이고 모델에 따라
역효과라는 것.

그런데 여기서 답하지 못한 질문이 남는다. **본 실험의 `allowed_field_paths`는 43개 시나리오
전부 사람이 썼다.** 그 작성 단계가 언제나 사람이어야 한다면 최소권한은 검토 인력에
비례해서만 확장된다.

그래서 같은 라벨을 **읽기만 하는** 별도 실험을 돌렸다. 업무 요청문과 도구별 반환 가능 필드
40개를 주고 모델이 직접 최소권한 정책을 쓰게 한 뒤, 인간 라벨과 비교했다.
**4모델 × 43시나리오 = 172콜, 파싱 실패 0 / 기술 실패 0.**

- 설계(결과 보기 전 고정): [`docs/policy_authoring_v3.md`](docs/policy_authoring_v3.md)
- 결과 전문: [`docs/policy_authoring_results_v3.md`](docs/policy_authoring_results_v3.md)

![오류 방향](docs/figures/fig_policy_error_directions.png)

**정확 일치 0/172.** 그리고 실패의 형태가 "너무 관대함"이 아니었다.

| | 시나리오당 |
|---|---|
| 인간 검토자가 허용한 필드 | 8.6 |
| 모델이 허용한 필드 | 5.7 |
| **과잉 허용** (검토자가 뺀 것을 줌) | **3.59** |
| **과잉 차단** (검토자가 준 것을 뺌) | **6.44** |

두 오류가 **동시에** 크다. 더 넓거나 좁은 정책이 아니라 **다른 정책**을 쓴다(Jaccard 0.18).

세 가지가 더 나왔다.

**① 모델은 과제를 읽고는 있다.** 검토자가 필요하다고 한 필드를 포함하는 비율(0.36~0.45)이
불필요한 필드를 포함하는 비율(0.05~0.12)보다 네 모델 모두 뚜렷이 높다. 고정 습관이 아니라
반응은 하는데 **감도가 낮다.**

**② 식별자를 빼먹어 검색 연결이 끊긴다.** `email.id` 95% · `calendar.id` 92% ·
`contact.id` 85% 누락. 이것이 본 실험의 미해결 관찰과 정확히 맞물린다 — 본 실험에서 모델은
평균 **1.45회**만 도구를 부르고 발견→상세 체인을 완주한 것은 **8.6%(59/688)** 였다.
**행동할 때 검색을 연결하지 못하고, 정책을 쓸 때 연결에 필요한 필드를 빼먹는다.**
두 실험이 독립적으로 같은 결함을 가리킨다.

**③ 민감 필드 위험은 한 곳에 몰려 있다.** 전체 콜의 18.0%가 금지된 민감 필드를 허용했는데,
`email.body`가 **24.3%(35/144)** 로 압도적이다(`contact.phone` 5.1%, `contact.notes` 2.7%).
연락처의 전화·메모는 "개인정보"로 보이지만, 메일 본문은 업무 문서로 보이고 그 안에 민감
정보가 있는지는 **내용을 봐야** 알 수 있기 때문으로 보인다.

### 4.4.1 그래서 사람은 어디에 필요한가

실패를 원인별로 나누면 사람이 필요한 지점이 좁혀진다.

| 실패 | 누가 잡나 |
|---|---|
| 도구 혼동 (과잉 허용의 **57%**) | **기계** — 적용 전 스키마 검증 |
| 경로 표기 오류 (어휘 밖 경로의 **88%**) | **기계** — 같은 검증기 |
| 식별자 누락 | **기계** — 검색 연결 가능성 정적 확인 |
| `email.body` 허용 (24.3%) | **사람** — 내용을 봐야 판단 가능 |

즉 **"AI 초안 → 스키마 검증기 → 사람은 자유서술 필드만 승인"**. 사람이 43×8.6 필드를 전부
보는 대신 본문·메모에 집중하면 된다는 것이 이 데이터에서 직접 나온다.

> **유보**: 43개 중 36개 시나리오에서 4모델 전원이 과잉 허용했다. 전원 불일치를 전부 모델
> 오류로 읽는 것은 무리이며, 우리 라벨이 일관되게 엄격할 가능성도 있다. 라벨은 이 실험을
> 위해 수정하지 않았고, 판단을 유보한 채 수치를 그대로 보고한다.

## 5. 말할 수 있는 것 / 없는 것

**말할 수 있는 것**
- task-aware 필드 projection은 **실제 전달되는 민감 필드를 0으로 만든다** (A−C 0.50, 95% CI 0.35~0.65, 4모델 동일).
- **프롬프트 최소화 지시는 전달을 줄이지 못한다** (중립 0.50 vs 지시 0.52).
- A/B에서는 **업무에 성공한 run조차** 민감 필드를 함께 전달했다.
- 필드 최소권한은 **설계상** 노출 용량을 93%(151.5→10.5) 줄이고, 악성 본문 전달 경로를 5→0건으로 없앤다.
- **도구 형식 미준수는 접근 지표를 오염시킨다** — 파일럿 게이트가 필요하다(`mistral:7b`의 "전달 0"은 프라이버시가 아니라 실패였다).

**아직 말할 수 없는 것**
- **projection이 "안전한 완수"를 늘리는가** — primary p=0.070, 검정력 부족.
- **필드 정책이 실제 인젝션 *행동*을 막는가** — 악성 본문이 모델에 도달한 사례가 없어 차단을 시험할 기회 자체가 없었다. clean/poisoned 공격쌍 실험이 따로 필요하다.
- 낮은 task 성공률이 **모델 능력 한계인지 validator 엄격성인지**.
- 악성 payload가 `body`가 아니라 subject·sender·calendar·notes에 있을 때도 같은 효과인지.
- 더 크고 tool-eager한 **상용 모델**에서도 같은 양상인지.

## 6. 라이브 데모 — 커밋된 run을 그대로 재생

```bash
python -m http.server 8080     # 이후 http://localhost:8080/demo/
```

**① Run replay (실측).** 시뮬레이션이 아니라 커밋된 `experiments/main-*/runs.jsonl`의 실제 로그를 턴 단위로 재생합니다. 모델·시나리오·좌우 조건을 고르면 같은 시나리오의 두 run이 나란히 나옵니다 — 왼쪽 A에서는 `notes`("식사 알레르기: 견과류")·`phone`이 **"민감 필드 전달됨"**, 오른쪽 C에서는 같은 `search_contacts` 호출인데 그 필드들이 **"모델에 전달 안 됨"** 으로 잘려 있습니다. `run_id`와 task/safe 배지까지 로그 그대로입니다.

로그에 원문이 없으므로(경로·해시·카운트만) 화면의 원문은 공개 합성 데이터를 로그의 레코드 ID × 필드 경로와 조인해 재구성합니다 — **이 재구성 규칙 자체가 privacy-safe 로깅 설계의 시연**입니다. 모델의 최종 답변은 저장하지 않았으므로 지어내지 않고 "미보관(sha256·글자수)"으로 표시합니다.

**② 개념 시연 (합성 예시).** 발표 도입용으로, 가상의 레코드에서 정책이 무엇을 잘라내는지 보여줍니다.

인덱스는 [`demo/build_replay_index.py`](demo/build_replay_index.py)가 `runs.jsonl`에서 생성합니다(run 추가 시 재실행). 디자인 톤은 [`DESIGN.md`](DESIGN.md).

# 부록

## A. v2 탐색 결과 (legacy · 인과 근거로 인용하지 않음)

v2는 4모델 × 48시나리오 × 4조건 × 1seed = **768 runs**로, 2절의 세 가지 교란 때문에 인과 해석이 성립하지 않습니다. 다만 **교란과 무관하게 유효한 두 가지**가 있어 남겨 둡니다.

- **설계 수준 노출 용량 계산** — 필드 필터 없음 151.5 / 악성 전달 5건, 필드 최소권한 10.5 / 0건 (정책 정의에서 계산되므로 실행과 무관).
- **필드 제거 기전이 실제로 작동함** — 같은 데이터에서 필드 필터 없는 조건의 도구 반환 로그에 연락처 `notes`의 민감 건강정보가 **69건**(A 35 / B 34) 전달됐고, 필드 최소권한 조건에서는 **0건**이었다. [`legacy_delivery_scan_v2.py`](legacy_delivery_scan_v2.py)로 재현.

그 외 v2의 접근량·성공률·trade-off 수치는 조건 A가 이미 최소화 지시를 포함했다는 사실 때문에 해석할 수 없습니다. 재현 명령:

```bash
python run_experiments_v2.py <model> --seeds 1
python analysis_experiment_v2.py ; python interface_risk.py ; python interface_realized.py ; python stats_v2.py
```

> `experiment.py`, `llm_agent.py`, `run_experiments_v3.py`, `run_paper_pipeline.py`는 v1/초기 탐색 코드입니다. 특히 **`run_experiments_v3.py`는 이름과 달리 v3 프로토콜과 무관한 옛 러너**이므로 본 실험에 쓰지 않습니다.
